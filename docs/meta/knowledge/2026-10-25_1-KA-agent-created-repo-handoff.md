# Передача владения репозиторием, созданным агентом

## Исходная ситуация

Агент создаёт репозиторий или папку от своего OS-пользователя. Человек,
который владеет работой, может не иметь прав на файлы; git может ругаться
на `dubious ownership`. Если просто сделать `chown`, агент потеряет доступ.
Если не сделать `safe.directory`, человек не сможет работать с git.

Это не проблема конкретного проекта, а типовой разрыв между агентом и
человеком. Он особенно заметен, когда агент создаёт инструменты и
репозитории самостоятельно.

## Приобретённое понимание

1. **Передача владения — часть создания.** Если агент создал папку или
   репозиторий для человека, он сразу оставляет инструмент передачи, а не
   вспоминает об этом позже.
2. **Один принятый инструмент — `handoff-to-owner.sh`.** Человек получает
   владение; агент сохраняет доступ через ACL; для git добавляется
   `safe.directory` обоим.
3. **Имена задаются явно.** `--owner` и `--agent` обязательны; в шаблоне нет
   захардкоженных пользователей. Это делает инструмент переносимым и не
   выдаёт приватное окружение.
4. **Два режима.** Скрипт можно скопировать в целевую папку и запустить как
   one-shot: он передаст владение и удалит себя. Можно запустить канонический
   инструмент с `--target`: он передаст владение, но останется на месте.
5. **Локальный exclude, не `.gitignore`.** В one-shot режиме имя скрипта
   добавляется в `.git/info/exclude`: этот файл локален, не коммитится и не
   клонируется. Он защищает от `git add .`, но не от `git add -f` или явного
   пути. `.gitignore` сделал бы временный операционный файл частью
   репозитория — это лишний шум.
6. **Скрытие — цена защиты.** Если скрипт не запустить, он может остаться
   незамеченным. Проверка после передачи: `test ! -e handoff-to-owner.sh`.
7. **Безопасность.** Скрипт требует root, отказывается работать для `/`,
   проверяет существование пользователей и `setfacl`, не меняет содержимое
   данных и не заменяет резервную копию.
8. **Проверка.** После передачи `git status` должен работать от человека и
   агента; скрипт должен исчезнуть в one-shot режиме.
9. **Reference-инструмент живёт в `tools/`.** Это осознанное исключение из
   правила «инструменты вне knowledge-репозитория»: инструмент маленький,
   self-contained, входит в onboarding методики и не имеет отдельного
   релизного цикла. Когда он вырастет, его вынесут в отдельный репозиторий.

## Как этим пользоваться

Практическая инструкция, требования и safety — в
[`tools/handoff-to-owner/README.md`](../../../tools/handoff-to-owner/README.md).

Коротко:

```bash
cp tools/handoff-to-owner/handoff-to-owner.sh /path/to/target/
printf '%s\n' 'handoff-to-owner.sh' >> /path/to/target/.git/info/exclude

sudo bash /path/to/target/handoff-to-owner.sh \
  --owner <human-user> \
  --agent <agent-user>
```

Или в reusable-режиме:

```bash
sudo bash tools/handoff-to-owner/handoff-to-owner.sh \
  --owner <human-user> \
  --agent <agent-user> \
  --target /path/to/target
```

## Когда не применять

- папка создана человеком, а не агентом;
- нет POSIX ACL и `setfacl`;
- нужен групповой или сервисный владелец — это отдельный сценарий;
- нужна передача прав на несколько машин и разные ОС — нужен отдельный
  runbook.

## Открытые вопросы

- как поступать без `setfacl`;
- как передавать владение на файловых системах без POSIX ACL;
- нужен ли отдельный `OWNERSHIP.md` помимо скрипта;
- когда инструмент пора выносить из `tools/` в отдельный репозиторий.
